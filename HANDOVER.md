# Handover

Everything a new person needs to run this, demo it, and not get caught out in a
review. Written to be honest about what is real and what is scaffolding, because
the difference matters when a panel asks.

Last verified: 4 September 2026, commit `58e219c`.

---

## 1. What this is

One assistant that finds wasted cloud spend across **two domains that are normally
separate tools**:

- **Infrastructure** — virtual machines. CPU, memory, disk, network.
- **AI services** — managed LLM inference. Tokens, model tier, latency, answer quality.

You type a question in plain English. A router decides which domain owns the
answer, and returns a ranked list of proposals — each with evidence, estimated
savings, confidence, business impact, and a prepared AWS Lambda payload that a
human must approve.

Nothing is ever executed. That is deliberate, not unfinished.

## 2. Running it

### Any platform

```bash
git clone <repo> && cd proactive-finops-agentic
python3 -m venv venv
source venv/bin/activate          # Windows PowerShell: .\venv\Scripts\Activate.ps1
pip install -r requirements.txt
python run_demo.py
```

Open <http://127.0.0.1:8000>. `--port 8010` if 8000 is taken.

Verified working from a completely fresh clone: no extra files needed, no
manual data setup. The SQLite database builds itself on first boot.

### macOS specifically

It works, with two caveats:

1. **Use Python 3.12.** The pinned `numpy==1.26.4` and `pandas==2.2.0` have no
   wheels for Python 3.13, so pip will try to compile them from source and fail
   on a stock Mac. `brew install python@3.12` then
   `python3.12 -m venv venv`.
2. **The local AI is easier on Mac than on Windows.** See section 4.

### What you get without any extra setup

Every question works. The AI-written summary falls back to text composed from
the evidence rather than generated by a model — the numbers are identical either
way. To get the generated prose, see section 4.

## 3. What is real and what is not

**Read this before any review.** Getting caught out here costs more than the
feature is worth.

| Part | Status |
|---|---|
| Infrastructure decisions | **Genuinely computed.** Percentiles over a 7-day window, per machine. |
| Forecasting | **A real trained model.** Random forest, evaluated on held-out data. |
| **AI-service decisions** | **Hardcoded per deployment name.** See below. |
| Cost figures | Synthetic, derived from published cloud pricing. Method is sound; numbers are not a real bill. |
| Telemetry | 2 machines real (CoreStack), 54 synthetic and labelled as such in every row. |
| Lambda execution | Simulated. The payload is built and logged, never sent. |

### The one to be upfront about

`ai_finops/storage.py::_generate_recommendations` decides AI-side actions like
this:

```python
if row["deployment_key"] == "bedrock-support-prod":
    action, savings_rate = "ENABLE_PROMPT_CACHING", 0.17
```

It is a lookup table keyed on deployment name. The `evidence` dictionary —
cacheable ratio, token counts — is attached **after** the decision is made, so it
looks evidence-backed while playing no part in the decision. The savings rates
(0.17, 0.68, 0.72) are invented constants.

If asked *"how do you detect the token waste?"*, the honest answer is that this
layer is scripted. Say it before someone finds it:

> "The infrastructure side computes everything from the telemetry. The AI side
> currently uses fixed rules per deployment — deriving those from the measured
> cache ratios and quality headroom is the next module."

A working evidence-driven version was written and then reverted (it changed the
demo numbers the day before a presentation). The approach that worked: score
every applicable option and pick the highest-saving one, rather than an if/elif
chain where whichever rule is written first masks larger savings further down.

## 4. The local AI model

Optional. The platform runs fully without it.

Copy `.env.example` to `.env` and set:

```bash
FINOPS_LLM_PROVIDER=ollama
OLLAMA_MODEL=qwen3:1.7b
```

Then `ollama pull qwen3:1.7b`.

`.env` is gitignored, so it does **not** come with a clone. A fresh clone will
report `policy_fallback` until you create one.

### Why qwen3:1.7b and not something bigger

Benchmarked on the original dev machine (6-core CPU, no usable GPU):

| Model | Wall | Output quality |
|---|---|---|
| llama3.2:3b | 7.6s | wrote placeholders like `[list the workload names]` |
| qwen3:1.7b, thinking **on** | 11.0s | truncated mid-sentence |
| **qwen3:1.7b, thinking off** | **4.8s** | named the actual deployments |

`think: false` mattered more than the model choice. Reasoning models spend the
whole token budget on hidden reasoning and return a truncated summary. The flag
is sent automatically; Ollama ignores it for models that do not reason.

### Windows/WSL vs macOS

On WSL, Ollama runs on the Windows side and is unreachable over HTTP from inside
WSL, so `ai_finops/llm.py` shells out to `powershell.exe`. **On macOS none of
that applies** — Ollama listens on `127.0.0.1:11434` natively, the HTTP path is
used, and it is faster. The PowerShell path is checked for existence first and
simply is not there on a Mac.

If the model is configured but unreachable, one failure parks it for 120 seconds
and the console silently falls back to evidence text. That is intentional: it
stops every question paying a timeout.

## 5. Gotchas that have already bitten us

**The forecast tab needs 4 minutes.** Models train in a background thread at
boot. Until they land, the tab shows "training models". Start the server five
minutes before any demo.

**The first AI question is slow.** Cold model load is ~26s, then ~5s, and it
stays warm for 30 minutes (`keep_alive`). Ask a throwaway question before
presenting.

**AI numbers shift slightly between regenerations.** The AI dataset is generated
relative to *now*, so rebuilding it moves the 30-day window and totals change by
a few dollars. Do not hardcode AI figures into slides without re-checking.

**Regenerating data means regenerating everything, in order:**

```bash
python tools/generate_fleet_telemetry.py       # must run first
python tools/generate_enterprise_context.py    # reads the telemetry
python tools/generate_multicloud_demo_data.py
```

Running the second without the first leaves inventory disagreeing with telemetry.

**`data/corestack_vm_metrics.csv` is gitignored** (8MB raw source). Nothing at
runtime needs it. Only `tools/augment_metrics.py`, the superseded generator,
reads it — so that script cannot run from a clone. This is fine;
`generate_fleet_telemetry.py` replaced it.

**Two bugs that were invisible without automated UI checks**, both worth knowing
because the same mistake is easy to repeat:

- `.drawer { display: flex }` overrode the `hidden` attribute, so an invisible
  panel sat over the page swallowing clicks. Fixed with a global
  `[hidden] { display: none !important; }`.
- `.bar-fill` was an inline `<span>`, and inline boxes ignore width and height,
  so **every bar chart rendered as an empty grey track**. Fixed with
  `display: block`.

**The recommendation logic was once tuned against flat data.** The old rule was
`max_cpu > mean + 1.5*std`. A daily peak exceeds that by definition, so once the
data became realistic it flagged 43 of 56 machines. If you change the data
generator, re-check the decision thresholds — they are coupled.

## 6. Layout

| Path | What it holds |
|---|---|
| `agents/unified.py` | **The router.** Classifies a question, merges both analysts into one `Decision` shape. Start here. |
| `agents/analyst.py` | Infrastructure decisions. Percentile logic. |
| `agents/forecasting.py` | The prediction model. |
| `agents/fleet.py` | Fleet totals and chart data. |
| `agents/datacache.py` | Caches the 118k-row CSV reads. Without it a question takes 1.1s instead of 0.005s. |
| `agents/core.py` | The action catalogue — every action, its label, tone and Lambda function. |
| `ai_finops/` | AI-service analyst, data foundation, LLM adapter. |
| `api/main.py` | 19 endpoints across both domains. |
| `frontend/` | The console. No build step, no CDN, works offline. |
| `tools/` | Data generators. Deterministic, seed 42. |
| `tests/` | 23 tests. `python -m unittest discover -s tests` |
| `docs/DATA_STRATEGY.md` | What may and may not be claimed about the data. Read before writing a report. |

### The design rule that holds it together

Both analysts emit an identical `Decision` — 21 fields, same names, whatever the
domain. That is why one screen renders a VM shutdown and an LLM model switch as
the same card. `test_decision_contract_is_identical_across_domains` enforces it
by diffing the two field sets and requiring zero differences.

**Any new analyst must fill the same contract.** Add actions to
`agents/core.py`, not inline.

## 7. Demo script

Server up five minutes early, one throwaway question asked.

1. **`Where can we save the most money across the estate?`** — 19 decisions,
   ~$5,584/month, servers and AI in one ranked list, under a second. The thesis.
2. **Click any decision.** Evidence, guardrail, prepared action. "A decision,
   not a graph." Note that nothing executes.
3. **Infrastructure tab.** All four signals. Inspect `testtruecost` — a nightly
   batch job that peaks at 02:00 and flatlines by day. Proves the data is real-shaped.
4. **`Which VMs need scale down?`** then mention `site-recovery-VM`: CPU 15%,
   memory 94%, and the system refuses to shrink it. Downsizing on CPU alone would
   have crashed it. This is the smartest thing in the build.
5. **`Which VMs need scale up?`** — 4 machines, medians 81/80/73%. It
   deliberately does not flag machines that merely spike; those need autoscaling,
   not a bigger box.
6. **Forecast tab.** Predicted vs actual on data the model never saw. 96% of real
   spikes called in advance on the batch machine.
7. **Activity tab.** Lambda payloads proposed, none executed.

Say the data provenance out loud before anyone asks: two real machines, 54
synthetic, every synthetic row labelled.
